## Каталог и варианты — Vercel Commerce + Medusa DTC

Стабильный option ID отделён от переведённой подписи. Выбранные значения доступны
через URL: refresh, ссылка и Back воспроизводят состояние. Изменение одного
значения сохраняет остальные параметры; фильтр/сортировка сбрасывает пагинацию
только соответствующего списка. Порядок и ключи не зависят от локализованного текста.

У товара различаются incomplete, invalid, missing combination, unavailable,
ambiguous и ready. Покупка возможна лишь при одном полностью определённом варианте;
сервер повторно проверяет его доступность. Нельзя угадывать товар при поддельном URL.
Для единственного варианта допустим предвыбор, если он однозначен. Смена варианта
согласованно меняет изображение, цену, остаток и ссылку, а не только подпись кнопки.
У нескольких групп опций проверить тупиковые сочетания и понятный сброс выбора.

Выбор силы, объёма, размера, сортировки и других параметров внутри текущего
сценария сохраняет положение чтения. Не выполнять полную перезагрузку или
сброс прокрутки к началу страницы при каждом выборе. URL обновлять согласованно
с выбранным состоянием; Back возвращает предыдущее состояние и положение.
В Next.js применять навигацию без прокрутки (например, `scroll={false}`);
в другом стеке использовать его механизм частичного обновления. При экспорте
не терять это поведение вместе с удалённым runtime: наличие атрибута в исходнике
не доказывает поведение опубликованной копии. Проверить живой экспорт нажатием
после прокрутки, а также обновление данных, последующее добавление в корзину,
клавиатурный фокус и Back. Переход к другой странице или явная команда «вверх»
имеют собственный сценарий прокрутки и не подчиняются этому правилу выбора.

Исполняемые извлечения: [variant-selection.mjs](../assets/commerce/variant-selection.mjs)
на основе Vercel и [option-filters.mjs](../assets/commerce/option-filters.mjs) на
основе Medusa. В них удалены зависимости Shopify/Medusa/Next/React, усилена
проверка значений и унифицированы повторяющиеся query-параметры. Это одна логика
для разных renderer, а не ещё одна независимая реализация внутри каждого блока.

Проверять: неизвестный ID; неполный выбор; отсутствующее сочетание; закончился
остаток после загрузки; несколько одинаковых сочетаний; длинные подписи;
сохранившиеся сортировка/кампания; Back; отсутствие результата и отказ провайдера.

### Модель вариантов и адрес

Google документирует одно- и многостраничную модель вариантов. Выбрать по
каталогу, содержанию и действующей архитектуре; не менять product ID/SKU или
разбивать товары в backend лишь ради адреса.

| Модель | Контракт |
| --- | --- |
| Одна страница товара с вариантами | Вариант открывается по устойчивому URL-состоянию; цена, медиа и наличие соответствуют выбору; canonical и `ProductGroup` описывают выбранную модель |
| Отдельные страницы вариантов | Каждый URL открывает нужный вариант непосредственно, имеет полезное содержание и согласованные canonical/разметку; страницы связаны между собой |

Один общий `ProductGroup` связывает варианты, если они действительно образуют
группу; разные самостоятельные товары не группируются только по бренду.
Профиль CBD И503 с отдельным товаром на силу и меру сохраняется в проектах,
где он выбран ([cbd-profile.md](cbd-profile.md)); это не доказательство
преимущества для любого ассортимента. Индексация, hreflang и sitemap —
[ecommerce.md](ecommerce.md), §4. Источник, проверен 06.10.2026:
[варианты Google](https://developers.google.com/search/docs/appearance/structured-data/product-variants).

## Цена и корзина — применяем принципы, не копируем чужую арифметику

Vercel показывает немедленный optimistic отклик, но его демонстрационный reducer
складывает `Number`-цены и заменяет tax/subtotal. В общей системе это не источник
денег. Medusa показывает цены из расчёта backend; её проверку через falsy нельзя
переносить: цена 0 не означает отсутствие цены.

### Деньги

Единственное место правил денег; vendure.md, platforms.md и ecommerce.md
ссылаются сюда.

Цена, итог, скидка, налог, доступность варианта и наличие подтверждаются
сервером (commerce backend); витрина не складывает цены. Источник определяет
currency, единицу суммы, точность, скидки, налог и доступность; цена передаётся с
валютой и точностью источника — не предполагать две дробные цифры для всех
валют и не считать суммы через произвольные float. Адаптер нормализует их один
раз; UI форматирует локаль одной функцией через Intl и не делит всегда на 100.
Компоненту не передаются необработанные SDK-объекты. Ноль, отсутствующее
значение, неподдержанная валюта и ошибка — разные состояния; недоступный
источник отличается от пустого каталога. «Цена от» не считается ценой
выбранного варианта. Разметка, интерфейс и feed, если он нужен, используют те
же данные. Денежную арифметику в компонентах меряет `check:port`, семья
`moneyMath` (таблица в [vendure.md](vendure.md)).

### Корзина

Для корзины: подтверждённый серверный snapshot + отдельное pending-намерение.
Optimistic отображение не подтверждает новый итог, налог, скидку или оплату.
Сериализовать конфликтующие записи на одну корзину или использовать серверные
ревизии; не принимать поздний ответ как более новый. Количество — конечное целое,
изменение по cart-line ID: одинаковый variant может иметь разные опции/подписки.
Локальный таймаут записи означает неизвестный результат, а не доказанный отказ;
перед повтором сверить backend. Не делать автоматический повтор неидемпотентного действия:
платёж и создание заказа требуют подтверждённой идемпотентности. Optimistic UI не
превращает клиент в источник истины об оплате и наличии.

[mutation-lane.mjs](../assets/commerce/mutation-lane.mjs) — наш небольшой ресурс:
пока запись идёт, вторая ОТКЛОНЯЕТСЯ (не ставится в очередь) — контрол выключен
и показывает ожидание; `timeoutMs` прерывает зависшую запись и освобождает полосу
с исходом «неизвестно» — корзина перечитывается до любого повтора; `subscribe`
даёт перерисовку (`useSyncExternalStore`). Это не распределённая блокировка:
другие вкладки и устройства требуют контракта backend. Ошибка остаётся видимой; вернуть кнопку недостаточно без сообщения.
При необходимости параллельного редактирования вводить очередь намерений и тесты
ревизий вместо удаления защиты. Network read и commerce mutation имеют разные правила повтора.

Проверять: двойное нажатие; ошибка/таймаут; поздний ответ; 0; last-item removal;
скидка на всю корзину; разные валюты/регионы; устаревший остаток; восстановление
после refresh. Не объявлять заказ оплаченным по redirect/query-параметру.

### Промокод и порядок действий в корзине

Для корзины с необязательным промокодом рекомендуемый порядок: раскрытие
«Есть промокод?» → применение кода → блок сумм со скидкой и итогом → переход
к оформлению. Это рекомендация по иерархии действия, а не юридическая норма
или вывод из перечисленных выше исходников. Поле меняет расчёт, поэтому
покупатель должен видеть обновлённый итог после применения и до Checkout.
Не ставить промокод отдельным хвостом после Checkout и «Продолжить покупки».

По умолчанию поле свёрнуто; при открытии ошибки и результат находятся рядом
с ним. Проверить применение, удаление, отказ и пересчёт на данных источника.
В боковом окне сохранить порядок и при прокрутке: раскрытая форма не должна
обрезать основное действие или занимать весь доступный экран. При нехватке
высоты применять [контракт окон](overlays.md), оставляя доступными итог и
переход к оформлению, а дополнительные поля — в прокручиваемой части.

## Пагинация и кэш — Hydrogen + Paper

Vendure и Payload листают номерами страниц (`take/skip`, `page/limit`):
для них — `pageVariables` из [search.mjs](../assets/vendure/search.mjs), мусорный
номер — 404. Курсоры ниже — для источников с курсорами (Shopify и подобные).
Кэш витрины на Next 16 — теги и `'use cache'`, раздел «Кэш» в [vendure.md](vendure.md);
HTTP-директивы ниже — для ответов собственных маршрутов.

[pagination.mjs](../assets/commerce/pagination.mjs) извлечён из Hydrogen:
cursor+direction и namespace для нескольких списков. Добавлены проверки размера,
разделение reset и сохранение фильтров. Provider переводит first/last/cursor в
аргументы своей платформы; UI сохраняет семантические ссылки и работает без
бесконечного скролла. При смене набора данных старый cursor не переиспользуется.

[cache-policy.mjs](../assets/commerce/cache-policy.mjs) использует подход Hydrogen
к явным HTTP-директивам. Personal/unknown/session unavailable и все mutation —
no-store; public только явно. Политика TTL относится к данным, не ко всему сайту.
Не кэшировать персональные HTML/цену по публичному ключу. Проверять Vary/CDN/cookies
и реальную стратегию framework: один заголовок не исправляет другой уровень кэша.

Из Paper принят единый реестр: ресурс → cache key scope → теги → TTL → события
инвалидации → затронутые страницы. Для ключа учитывать locale/channel/currency
и применимые фильтры. CMS изменение обновляет страницу и её списки; смена slug —
старый и новый URL. Метаданные реестра могут обслуживать диагностику без
секретов и клиентов. Кэшировать публичный каталог согласно версии фреймворка;
сессии покупателей не смешиваются.

### Подписанный webhook сброса кэша

Единственное место правила; vendure.md и payload.md описывают только отправителя
своего движка. Источник (плагин Vendure, хук Payload) шлёт каждой витрине
подписанный POST на `/api/revalidate`: HMAC по телу и времени, сравнение
`timingSafeEqual` (не `===` — подбор секрета по времени ответа), окно повтора
5 минут, теги старого и нового состояния; витрина раскрывает базовый тег по всем
языкам и валютам канала. Подпись, защита replay и минимальные права обязательны
для конкретного adapter. При неполном payload — ограниченный fallback в том же
канале, а не бесконтрольный global purge. Webhook-пример не копировать без
проверки этой границы и затронутых страниц списка.

Проверять изменение навигации/футера, редактирование товара, прежний URL, два
канала, две локали, ошибку сессии и webhook без части контекста. Default guest
нельзя подставлять при недоступной авторизации.

## Checkout и расширения — Paper

Принят подход явного registry доступных способов оплаты и отдельного контракта
их UI/server действий: capabilities, feature flags, submit mode, pending/error,
подтверждение статуса. Не смешивать разрешённый, недоступный, неизвестный и тестовый
gateway; dummy не включать в production. Возможности для UI подтверждает сервер,
публичный feature flag не является авторизацией. SDK и ключи остаются в своих слоях.

Шаги checkout имеют адресуемое состояние и Back; переход не стирает уже введённое.
Сервер проверяет предшествующие условия независимо от URL шага. Guest order URL
не раскрывает данные по угадываемому ID; доступ к заказу проверяется отдельно.
Транспортная ошибка сессии отличается от гостя. Платёжные секреты и сырые токены
backend не отправляются в browser storage, логи и документ передачи.

Это принятые архитектурные требования. FSL-код Saleor не скопирован и не
переведён в другую лицензию; реализация для Vendure/WooCommerce использует API
их версии. Не обещать отсутствие будущих изменений: провайдеры и контракты меняются.
Скилл должен заранее задать проверки этих границ, а не скрыть их за готовым UI.
